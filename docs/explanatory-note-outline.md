# Каркас пояснительной записки

## 1. Введение

- Актуальность автоматизации инфраструктуры и подхода Infrastructure as Code.
- Цель работы: разработать декларативный CLI-инструмент управления инфраструктурой Yandex Cloud.
- Задачи:
  - проанализировать предметную область IaC;
  - определить требования к системе;
  - спроектировать архитектуру приложения;
  - реализовать прототип на Python с использованием SDK;
  - протестировать основные сценарии работы.
- Объект исследования: процессы управления облачной инфраструктурой.
- Предмет исследования: методы декларативного описания и автоматического применения инфраструктурных конфигураций.

## 2. Аналитический раздел

- Понятие IaC и различие между декларативным и императивным подходами.
- Обзор существующих решений:
  - Terraform;
  - Pulumi;
  - CLI и SDK-подход.
- Обоснование выбора Python:
  - выразительность и читаемость;
  - развитая экосистема;
  - удобство построения CLI-инструментов.
- Обоснование выбора Yandex Cloud SDK:
  - прямой доступ к API провайдера;
  - контроль над логикой планирования и выполнения;
  - учебная ценность для демонстрации ООП-подхода.

## 3. Проектирование

- Функциональные требования:
  - валидация манифеста;
  - построение плана изменений;
  - применение инфраструктуры;
  - удаление инфраструктуры;
  - хранение локального состояния.
- Нефункциональные требования:
  - расширяемость;
  - читаемость;
  - безопасность хранения учетных данных;
  - устойчивость к частичным сбоям.
- Архитектура модулей:
  - CLI;
  - загрузка и валидация манифеста;
  - планировщик;
  - исполнитель;
  - фасад облачного провайдера;
  - хранилище состояния.
- UML:
  - диаграмма классов для обработчиков ресурсов и команд плана;
  - диаграмма компонентов;
  - диаграмма последовательности для сценария `apply`.
- Паттерны проектирования:
  - `Facade`;
  - `Factory`;
  - `Command`;
  - `Template Method`.

## 4. Реализация

- Выбранные технологии:
  - Python 3.12+;
  - Typer;
  - PyYAML;
  - Pydantic;
  - Yandex Cloud SDK;
  - pytest.
- Структура проекта и назначение основных файлов.
- Формат YAML-манифеста.
- Алгоритм построения плана:
  - `create`, если ресурса нет в локальном состоянии;
  - `replace`, если изменилась конфигурация ресурса;
  - каскадная замена зависимых ресурсов;
  - `noop`, если конфигурация совпадает.
- Алгоритм выполнения плана:
  - удаление заменяемых ресурсов в обратном порядке зависимостей;
  - создание ресурсов в прямом порядке;
  - сохранение `state.json` после каждого шага.

## 5. Тестирование

- Unit-тесты:
  - загрузка манифеста;
  - валидация ссылок и путей;
  - сериализация состояния;
  - построение плана;
  - порядок выполнения команд.
- Интеграционное тестирование:
  - применение реальной инфраструктуры;
  - повторный `plan` без изменений;
  - удаление ресурсов и очистка состояния.
- Ограничения MVP:
  - нет частичных точечных обновлений;
  - набор ресурсов ограничен сетью, подсетью и ВМ;
  - работа строится вокруг одного манифеста.

## 6. Заключение

- Перечень достигнутых результатов.
- Практическая ценность разработанного инструмента.
- Возможные направления развития:
  - поддержка нескольких экземпляров ресурсов;
  - поддержка дополнительных сервисов;
  - импорт существующей инфраструктуры;
  - web-интерфейс;
  - более гибкая политика обновлений.
